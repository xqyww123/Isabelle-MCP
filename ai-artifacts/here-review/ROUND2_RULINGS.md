## [dismissed] regressions-roots-uri-authority-yields-bogus-root: project_root_from_roots turns `file://<authority>/...` into a nonexistent directory under the cwd

The only named trigger cannot reach the code, and I measured it rather than reasoning about it. `_adopt_client_roots` builds its list from `ctx.list_roots()`, whose elements are pydantic-validated `mcp.types.Root` with `uri: FileUrl`; running that model in this venv gives 'file://localhost/home/x' -> 'file:///home/x' and 'file://LOCALHOST/home/x' -> 'file:///home/x' (WHATWG normalizes a `localhost` host on a file URL to empty). So the concern's own example never reaches project_root_from_roots in the spelling it describes. Only a genuinely non-empty host (a Windows UNC root) survives, and no client is named that emits one. The stripping itself is in `uri_to_file_path`, which I confirmed is byte-identical at HEAD (`git show HEAD:src/isabelle_mcp/utils/core.py` lines 182-185) with three other pre-existing callers, so 'a robustness gap in new code' is not accurate. And the degradation is bounded: relativize's `return real if rel.startswith("..") else rel` only makes paths print absolute, and a resolve_path into a nonexistent tree fails visibly. The suggested `os.path.isdir` guard would also put a filesystem probe inside a pure path function and silently drop roots on a not-yet-mounted network mount.

## [dismissed] regressions-integration-test-unrealpathed-root: The new integration test passes an un-realpath'd tmp_path as project_root

The trigger does not exist, and I checked pytest itself rather than the argument: `_pytest.tmpdir.TempPathFactory.getbasetemp` (pytest 9.0.3, the version in this venv) calls `.resolve()` in BOTH branches — `basetemp = basetemp.resolve()` for --basetemp and `temproot = Path(from_env or tempfile.gettempdir()).resolve()` otherwise — and additionally raises if the root is a symlink (`if stat.S_ISLNK(rootdir_stat.st_mode)`). So `str(tmp_path)` is already a real path, including the macOS /var -> /private/var case the concern names. `project_root=str(tmp_path)` is also the settled convention of this suite: seven pre-existing integration fixtures spell it that way (test_blob_query_tools.py:57, test_blob_breakpoints.py:89, test_cancel_z.py:74, test_debugger_e2e.py:343, test_ranged_sync_probes.py:80, test_debugger_probes.py:109 and :516, test_query_tools_e2e.py:106), and one of them already asserts a relativized short path (test_debugger_e2e.py:80), so if the hazard were real it would break there first. Applying the one-line realpath to this file alone would be a provable no-op that makes it the odd one out.

## [dismissed] elegance-optional-path-argument-order: `_optional_path` inverts the argument order of the `resolve_path` it wraps

A taste preference between two conventions that both have anchors in this tree, and the proposal is not strictly better. I checked HEAD: `(client, path)` is this repo's pre-existing signature shape for client-holding path wrappers in BOTH directions of the conversion — `_display_path(client, file_path)` wrapping `relativize(path, root)` (nine call sites at HEAD) and the now-deleted `_normalize_ref_path(client, path)` wrapping the same join. So `_optional_path(client, file_path)` follows the server/debugger-layer convention while `resolve_path(path, root)` follows the pure-utility convention in utils/core.py; the adjacency of the two spellings is the ordinary seam between those layers. The suggested `(file_path: str | None, root: str | None)` also makes both parameters the same type, so an accidental swap would type-check silently, whereas the current shape makes it an error under the project's configured mypy. No behaviour, no output, no test touched; the concern's own kind field is 'nit'.
